What is GitHub

GitHub is an online platform where you keep project folders (called "repos"). Every saved change stays in the history, you can share them, you can have parallel versions of the same project. It's free up to 2,000 minutes/month of automations on private repos. On public repos it's free and unlimited.

The 4 things about GitHub we need:

  • Repo: the online project folder
  • Issue: digital sticky notes with tasks
  • Pull request: proposed changes to the project, to be approved before they take effect
  • Actions: automations that run on a GitHub computer at the times or events you decide
The point: you need a place to give Claude instructions, schedule when it should run, see history, and review its work. GitHub does all of this, it's free, and Claude Code slots into it as the executor.

Trick 1 — Persistent memory: rules once, valid forever

Every new Claude Code session starts from zero. It doesn't know you want output in English, it doesn't know your tone of voice, it doesn't know which files it shouldn't touch. You repeat it every time.

Solution: put a file called CLAUDE.md at the root of the repo. Claude Code reads it automatically at the start of every session. Write the rules once, they always apply — even for sessions running in the cloud.

What it solves

  • Stop repeating conventions every session
  • If you work in a team, every colleague (and their Claude) follows the same rules
  • Also valid for scheduled runs (Trick 3) and automatic issues (Trick 4)

What to put in it

Example from our repo:

## Conventions - Output language: English - Brief: markdown, max 400 words - No secrets committed (they live in GitHub Secrets) - Branch: auto/<date>-<slug>, never directly on main - Style: direct, dry ## Key files | File | When to touch it | |---|---| | competitors.json | When you change competitors | | prompts/daily-brief.md | Only if you change brief structure | | .github/workflows/* | Only if you change cron or trigger |

It's a text file. You edit it with VS Code. You save it in the repo. From that moment, every Claude Code that enters the repo knows these rules before starting.

Ready-to-use example: materiali/CLAUDE.md.

Trick 2 — 3 Claudes in parallel (without stepping on each other's toes)

You have 3 independent tasks to do today. One at a time you waste time. Three Claudes in the same folder step on each other (they modify the same files).

Solution: git worktree. Create 3 subfolders, each is an independent copy of the project on a different branch. Each Claude works in its own subfolder. The original (main) stays untouched until you choose what to save.

What it solves

  • Triple your speed on days with multiple independent tasks
  • You can try 2 versions of the same change in parallel, pick the best, throw away the other
  • Experiment risk-free: if a Claude takes a direction you don't like, remove the subfolder and everything disappears

How to do it

  1. Create the 3 subfolders
    git worktree add .worktrees/add-delta -b feat/delta git worktree add .worktrees/change-model -b feat/model git worktree add .worktrees/fix-linkedin -b fix/linkedin

    Each is a copy of the project on a dedicated branch.

  2. Open 3 Claude Codes (3 Desktop windows)

    In each you enter a subfolder and give the task:

    cd .worktrees/add-delta claude > add Delta Corp to the competitors (website: delta.example.com)
  3. Wait for them to finish

    The 3 Claudes work in parallel, each on its own copy.

  4. Decide what to keep

    Result you like → open a pull request. Result you don't like → remove the subfolder, everything disappears.

    cd .worktrees/add-delta gh pr create --fill

Full pattern: materiali/docs/worktree-pattern.md.

Trick 3 — Scheduled work in the cloud (even with your PC off)

You want a report every morning at 7. You can't keep your PC on all night. Local cron isn't enough.

Solution: GitHub Actions. A YAML "recipe" that tells GitHub "at 7:05 every day, take this repo, install Claude Code, have it execute prompt X, open a pull request with the result". GitHub runs everything on its own server. You do nothing.

What it solves

  • The system runs even with your PC off, on vacation, on holiday
  • Negligible cost: GitHub Actions free up to 2,000 private minutes/month. One run = 30-60 seconds → ~30 minutes/month. Anthropic API: ~$0.30-1.50/month
  • You only get the result ready for approval

How to do it

  1. Save the API key in GitHub's vault

    GitHub has a system for credentials (Secrets). Once in, they're masked — you can't read them, only use them in workflows.

    gh secret set ANTHROPIC_API_KEY
  2. Open the workflow in the materials

    The file .github/workflows/daily-brief.yml is already prepared. The important part:

    on: schedule: - cron: "5 7 * * *" ← "every day at 7:05" steps: - launch Claude Code with the prompt in prompts/daily-brief.md - when done, open a pull request with the result
  3. Manual test (so you don't wait until tomorrow morning)
    gh workflow run daily-brief.yml

    1-2 minutes later, a pull request appears in your repo:

    📊 Daily Competitor Brief — auto #42 bot: github-actions new file: briefs/2026-05-08.md (+34 lines)

    You open, read, approve. From tomorrow morning it happens by itself.

Ready workflow: materiali/.github/workflows/daily-brief.yml. Full setup: docs/github-actions-setup.md.

Trick 4 — Delegate tasks from your phone in 30 seconds

An idea comes to you while you're out: "it would be nice to add Delta Corp to the competitors". Normally: go home, open PC, launch Claude, explain, check, save. 5-10 minutes.

Solution: open the GitHub app on your phone, write an issue (digital sticky note) with the task, add the label claude-task. A GitHub Action listens for the "label added" event, passes the issue text to Claude, it implements the change and opens a pull request. When you get home you have a proposal ready for approval.

What it solves

  • Capture ideas on the fly from your phone without opening the PC
  • You have a visible backlog: all repo issues, each with status (open, in progress, closed)
  • A colleague or a client can also open an issue and Claude processes it
  • Everything tracked: 6 months from now you know what was done, when, and who requested it

How to do it

  1. Create the label in the repo
    gh label create claude-task --color "8B5CF6" --description "Task to delegate to Claude"
  2. Set up the workflow in the materials

    The file issue-task.yml. Logic:

    WHEN: a "claude-task" label is added to an issue THEN: 1. take the issue title + description 2. pass them to Claude as a prompt 3. have it implement the change 4. open a pull request that closes the issue
  3. Test from phone or browser

    Open the repo → Issues → New issue:

    Title: Add Delta Corp to the competitors Description: Add Delta Corp as 4th competitor. Website: delta.example.com Pricing: delta.example.com/pricing LinkedIn: linkedin.com/company/delta Label: claude-task

    Submit. 1 minute later you find a pull request with the updated file.

The pattern: issue = command, label = submit, pull request = response. If you don't like the result, you don't approve and everything stays as it was.

Ready workflow: materiali/.github/workflows/issue-task.yml.

Trick 5 — Automatic quality check before saving

You're about to save changes. Maybe there's a password accidentally copied inside, a private note, a forgotten FIXME.

Solution: a "pre-commit hook". It's a script that git runs automatically before every save. The script sends the changes to Claude and waits for an OK or a BLOCK. If Claude finds a problem, the save fails and tells you what to fix.

What it solves

  • No more passwords committed by accident (real problem: bots scan GitHub in real time)
  • No more forgotten private notes or FIXMEs
  • Works automatically on every save, without you having to remember
  • If everything's clean it doesn't bother you: the review is instant (~2 seconds)

How to do it

  1. Activate the script in the repo

    The script is already ready in the materials. You copy it into .git/hooks/ and it becomes active:

    cp .github/hooks/pre-commit-claude-review.sh .git/hooks/pre-commit chmod +x .git/hooks/pre-commit
  2. What it does, in English

    5 lines that tell Claude: "see what I'm about to save? Reply 'OK' if it's clean, 'BLOCK: reason' if you see a serious problem (password, notes, FIXME)". If BLOCK, the save doesn't go through.

  3. Practical test

    You try to save a change with an API key inside:

    🔍 Claude review in progress... ❌ BLOCK: possible API key detected in config.txt line 12 Looks like an Anthropic key (sk-ant-...). To bypass (at your risk): git commit --no-verify

    Disaster avoided. Remove the key, save again, it passes.

The bypass --no-verify exists for cases where you're sure it's a false alarm. It adds a small friction that makes you think twice.

Ready script: materiali/.github/hooks/pre-commit-claude-review.sh.

Other practical uses of the same pattern

The competitor brief example is one of a thousand ways these 5 tricks combine. The cases below are done with the same materials files — only the prompt changes.

Daily lead qualification Scheduled action that every morning reads new leads from the CRM (via API), qualifies them with Claude according to your ICP written in CLAUDE.md, opens a pull request with the report.
Weekly reputation audit Every Monday at 9: Claude searches for brand mentions on the web, classifies positive/negative/to-respond, opens a report. For each comment to handle you open an issue from the phone with the link, label claude-task, and Claude drafts the reply.
Internal knowledge base editable by anyone The wiki lives in the repo. A colleague sees a procedure to update, opens an issue, labels it claude-task. Claude updates the file and opens a pull request. No more "the official document is the one Marco has on his Drive".
Social content generation You keep ideas in an ideas.md file. 3 times a week an Action takes the next idea, Claude turns it into a LinkedIn post respecting the tone in CLAUDE.md, opens a pull request. You approve and copy it to LinkedIn.
Onboarding new collaborators The project's CLAUDE.md is also the onboarding manual: anyone entering the repo (human or AI) starts aligned.

The pattern: rules in CLAUDE.md + parallel copies with worktrees + cloud execution with Actions + backlog with issues + quality check with hooks. Only what Claude does changes.
