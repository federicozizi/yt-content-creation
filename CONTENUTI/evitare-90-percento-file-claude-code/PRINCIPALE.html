Come evitare il 90% dei file inutili che Claude Code genera

Spiegazione del metodo: le 5 leve che disciplinano l'output
Cos'è questo documento. Materiale di supporto per capire e spiegare il metodo mentre registro: com'è fatto, dove agisce ognuna delle 5 tecniche, e — soprattutto — quanto fa scendere il numero di file, che è la tesi del video. Non è un copione da leggere: è lo schema mentale + i grafici da tenere davanti (e da mostrare a schermo). Le frasi le dico a braccio.
Il problema

Perché Claude Code riempie la cartella

Non è un bug: è una scelta di addestramento. Il modello è incoraggiato a "mostrare il proprio lavoro" — scrive piani di test, lascia note, sommari delle modifiche, scratch dei suoi ragionamenti. Per un developer esperto a volte è utile; per chi non è developer è rumore.

Risultato: chiedi una cosa semplice ("aggiungi un campo al form") e ti ritrovi 5 file che non avevi chiesto (TEST_*.md, NOTES_*.md, scratch_*.py, debug_*.md, summary_*.md). Dopo due settimane la cartella è illeggibile: difficile distinguere i file veri, difficile fare commit puliti, e a volte cancelli per sbaglio quello giusto. La buona notizia: questo comportamento si disciplina. Claude è istruibile — bastano le leve giuste, nei punti giusti.

Dove si agisce

Architettura del metodo

Tra la tua richiesta e il file scritto su disco ci sono tre punti in cui si può fermare un file inutile. Le 5 tecniche non sono in fila: sono 5 reti a maglie diverse piazzate su quei tre punti. Più reti metti, meno passa.

Punto A — istruzioni (Tecniche 1, 4, 5) Punto B — permesso negato (Tecnica 2) Punto C — hook che blocca (Tecnica 3) File inutile fermato Cartella pulita

Le tre tecniche del Punto A convincono Claude a non volere il file. Se per qualche motivo ci prova lo stesso (sessioni lunghe, "dimenticanza"), il Punto B lo rifiuta a livello di sistema e il Punto C lo intercetta con uno script. È la difesa a strati: ridondante apposta.

Pezzo per pezzo

Le 5 tecniche, una per una

1

Output Discipline nel CLAUDE.md Punto A · 10 min

Cos'è: una sezione ## Output Discipline nel CLAUDE.md del progetto — il file che Claude legge per primo a ogni sessione, la "costituzione" del progetto. Perché funziona: Claude rispetta il CLAUDE.md per default, quindi è la leva col miglior rapporto sforzo/effetto. Com'è fatta: tre regole — (a) lista esplicita di nomi banditi (TEST_*.md, NOTES_*.md, SCRATCH_*, debug_*, summary_*, duplicati tipo README_NEW.md); (b) niente sommario come file, lo dà in chat; (c) niente file di "ragionamento" — per gli stati intermedi usa il TodoWrite, non file su disco. Blocco pronto in esempio-claude-md.md. Limite: su task lunghi a volte lo "dimentica" — ecco perché serve la 2.

2

Deny patterns nel settings.json Punto B · 5 min

Cos'è: una sezione permissions.deny in .claude/settings.json che rifiuta la scrittura su certi nomi di file. Perché funziona: agisce a livello di sistema, non di prompt — anche se Claude prova a scrivere il file, il tool Write fallisce con "Permission denied" e lui se ne accorge. Bypassa la "dimenticanza" della Tecnica 1. Com'è fatta: i nomi si scrivono in formato glob (con asterischi): Write(**/TEST_*), Write(**/NOTES_*), Write(**/scratch*.*), e così via. Una sezione allow gemella protegge i tuoi test veri (**/*.test.js, **/tests/**) così non li blocchi per errore. File pronto: esempio-settings.json. Attiva appena salvi, senza riavviare.

3

Hook PreToolUse Write — il guardiano attivo Punto C · 15 min

Cos'è: un piccolo script che Claude Code esegue prima di ogni scrittura. La più tecnica delle cinque, ma anche la più potente. Perché funziona: il deny della Tecnica 2 guarda solo il nome; l'hook guarda anche il contesto — quanti .md ci sono già nella cartella, se è un duplicato (_v2, _copy), il contenuto. Com'è fatta: nel settings.json, hooks.PreToolUse con matcher: "Write" richiama node ~/.claude/check-write-discipline.js. Lo script legge la richiesta, e se viola le regole stampa "BLOCKED" e torna un errore: Claude desiste e mi spiega tutto in chat. Nota regista: lo script completo non è nei materiali — è nel video con un gist GitHub linkato. Tienilo pronto durante la registrazione.

4

Skill "Output minimalista" — la versione portatile Punto A · 15 min

Cos'è: le stesse regole impacchettate in una skill a livello utente (~/.claude/skills/output-minimalista/SKILL.md), che vale per tutti i progetti. Perché funziona: le skill si attivano da sole quando Claude riconosce che servono, senza ripetere la sezione output discipline in ogni CLAUDE.md. La fai una volta sola. Com'è fatta: un file SKILL.md con frontmatter (name + description che dice quando attivarla) e l'elenco di regole + l'eccezione "se l'utente chiede esplicitamente un file, crealo". Limite: meno deterministica del deny — funziona la gran parte delle volte, ma per blindare al 100% va abbinata alle Tecniche 1 e 2. Sinergia, non sostituzione.

5

Prompt iniziale rinforzato — il richiamo che funziona sempre Punto A · 10 sec

Cos'è: la cima dello stack. Il primo messaggio di una sessione importante non è la richiesta, è un blocco di reminder delle regole di output discipline. Perché funziona: su sessioni lunghe la pressione del task fa "scivolare" le regole del CLAUDE.md; il reminder le rimette in testa. Com'è fatta: tre cose — riassunto regole, eccezioni esplicite ("se ti chiedo crea il file X, fallo"), e una parola di richiamo: DISCIPLINE. Se durante la sessione Claude torna alle vecchie abitudini, le mando solo quella parola e lui rilegge le regole. Blocco pronto in prompt-tipo.md (con la variante "task brutale" per sessioni lunghe).

La tesi del video

Quanto scende il numero di file

Il metodo è puramente numerico e visivo: si passa da una cartella sporca a una pulita. I numeri qui sotto sono il caso reale mostrato nel video — lo stesso progetto (progetto-cliente-XYZ/), prima e dopo due settimane con le tecniche attive.

Prima vs dopo — numero totale di file nella cartella:

Prima (senza tecniche)
32 file  ·  di cui ~25 inutili
Dopo (5 tecniche attive)
8 file  ·  tutti utili

Da 32 a 8 file totali (−24). Ma il numero che conta è sui file inutili: erano ~25, vanno a ~0. È il ~90% di rumore eliminato — la promessa del titolo, presa alla lettera.

Quanto ne ferma ciascuno strato — % di file inutili evitati man mano che impili le tecniche (livelli mostrati nel video):

Solo Tecnica 1
~60%
Tecniche 1 + 2
~70%
Tecniche 1 + 2 + 5
~80%
Tecniche 1 + 2 + 3 + 5
~90%  ·  livello del video
Tutte e 5 + skill cross-project
~95%  ·  ogni progetto futuro

Percentuali indicative (esempio dal campo, non misura di laboratorio): servono a far capire allo spettatore fino a dove salire in base a quanto controllo vuole. Le Tecniche 1+2 da sole prendono già la gran parte, in ~15 minuti.

Le 1 e 2 sono "metti e dimentica" e da sole valgono già la gran parte del risultato. La 5 è "applica ogni volta" ma costa dieci secondi. La 4 si fa una volta nella vita e copre tutti i progetti futuri.

Onestà

Quando il metodo NON va applicato

A volte quei file servono davvero. Se sei developer e usi i piani di test o i log di debug per lavorare, la lista dei nomi banditi va tagliata su misura — non bandire ciò che ti serve.

L'eccezione esplicita è sacra. Tutte le tecniche lasciano passare il file se lo chiedi tu ("crea il file X"): è voluto. Il metodo disciplina i file non richiesti, non ti lega le mani.

I deny pattern sono permalosi. Un glob scritto male non blocca nulla (o blocca troppo): prima prova con un solo pattern e verifica che funzioni davvero. E proteggi i test veri con la sezione allow.

La skill non è deterministica al 100%. Si attiva "quando Claude pensa che serva": ottima come rete portatile, ma per blindare un singolo progetto tieni comunque le Tecniche 1 e 2.

La cartella che consegni

Cosa c'è nei materiali

È la cartella materiali/ che lo spettatore scarica e che tu zippi a fine video. Non è un programma da lanciare: sono esempi e regole già scritti, da copiare nei punti giusti del tuo progetto. Ecco com'è fatta e dove va ogni pezzo.

FileCos'è / a cosa serve
README.mdLa guida passo-passo per il pubblico: le 5 tecniche in versione operativa, con la tabella riassuntiva, il prima/dopo della cartella e i link alla documentazione. È il punto di partenza da cui leggere tutto il resto.
esempio-claude-md.mdUn CLAUDE.md di esempio già pronto (Tecnica 1). Contiene il blocco ## Output Discipline con i nomi banditi e le regole. Si copia come CLAUDE.md nella radice del tuo progetto: è la "costituzione" che Claude legge per prima.
esempio-settings.jsonUn settings.json di esempio (Tecniche 2 e 3). Dentro: la sezione permissions.deny coi pattern di file da rifiutare, la sezione allow che protegge i tuoi test veri, e l'hook PreToolUse Write. Si copia in .claude/settings.json (nel progetto) o ~/.claude/settings.json (per tutti i progetti).
prompt-tipo.mdIl blocco di reminder da incollare a inizio sessione (Tecnica 5), con anche la variante "task brutale" per le sessioni lunghe. Non si copia in un file di config: si tiene a portata di mano e si incolla come primo messaggio quando avvii un task importante.

In una riga: i pezzi non formano un flusso "input → programma → output", ma una difesa a strati che monti tu nel tuo progetto. Il blocco di regole di esempio-claude-md.md va nel CLAUDE.md del tuo progetto (Punto A); i deny pattern e l'hook di esempio-settings.json vanno nel .claude/settings.json (Punti B e C); il prompt-tipo.md lo incolli all'inizio delle sessioni lunghe (Punto A). Il README.md è la mappa che spiega quale pezzo va dove. La Tecnica 4 (la skill portatile) è descritta nel README ma non ha un file dedicato: la crei tu in ~/.claude/skills/ seguendo le istruzioni.

Provalo — parte operativa

Come testare il metodo (coi materiali del corso)

Qui non c'è un programma da lanciare: c'è un metodo. Il test serve a dimostrare, con gli occhi, che le tecniche fanno davvero scendere il numero di file. Tutto il necessario è nella cartella materiali/ (esempio-claude-md.md, esempio-settings.json, prompt-tipo.md). Si fa su un progetto-cavia, usa e getta, così non rischi nulla di tuo.

  1. Crea una cartella di prova vuota (es. progetto-cavia/) e aprila in VS Code. È il campo di prova: quello che generi qui lo puoi buttare.
  2. Applica i materiali. Copia il blocco ## Output Discipline da esempio-claude-md.md dentro un CLAUDE.md nella cartella; copia esempio-settings.json in .claude/settings.json (sono i deny pattern della Tecnica 2, più l'hook PreToolUse della Tecnica 3). Salva: valgono subito, senza riavviare.
  3. Dai a Claude Code un compito che di solito sporca la cartella — tipo: «aggiungi un campo email al form e fammi un riepilogo». È la richiesta che, senza disciplina, ti lascerebbe dietro summary_*.md, NOTES_*.md, file scratch.
  4. Osserva e conta. Verifica che NON spuntino i soliti file inutili; prova anche a chiedere esplicitamente un file-spazzatura (es. «scrivi un file summary_modifiche.md») e guarda il deny/hook rifiutare la scrittura. Conta i file prima e dopo.

Cosa devi vedere — quando Claude prova a scrivere un file bandito, il tool Write viene rifiutato a livello di sistema (esempio reale dai pattern in esempio-settings.json):

> aggiungi un campo email al form e poi scrivi un file summary_modifiche.md

  Modifico il form...  OK  (registrazione.js aggiornato)

  Write(progetto-cavia/summary_modifiche.md)
  -- Permission denied: "Write(**/summary_*)" e' nella deny list (settings.json)

  Ho aggiornato il form col campo email.
  Il riepilogo delle modifiche te lo do qui in chat, non come file:
   - aggiunto campo "email" (required) al form di registrazione
   - aggiunta validazione lato client e lato server

Nessun file extra creato.  summary_modifiche.md  ->  BLOCCATO
La prova che il metodo funziona:
  • La cartella resta pulita: dopo il task ci sono solo i file veri (il form modificato, il CLAUDE.md), nessun summary_* / NOTES_* / scratch → le tecniche del Punto A hanno convinto Claude a non volerli.
  • I Write-spazzatura vengono bloccati: anche forzando un nome bandito, il Write torna «Permission denied» e Claude desiste → il deny della Tecnica 2 regge la «dimenticanza».
  • Il conteggio file resta basso: sullo stesso progetto del video si passa da ~32 a ~8 file (di cui gli inutili: da ~25 a ~0) → è il ~90% di rumore eliminato, la promessa del titolo.

Due prove extra (facoltative):

• Spegni e riaccendi una rete. Togli temporaneamente esempio-settings.json (rinominalo) e rilancia lo stesso task: i file-spazzatura tornano a passare. Rimettilo: spariscono. Hai visto la Tecnica 2 accendersi e spegnersi.

• L'eccezione è sacra. Chiedi esplicitamente un file che ti serve davvero (es. «crea guida-utente.md»): viene creato senza problemi. Il metodo disciplina i file non richiesti, non ti lega le mani.

Nota: i numeri 32 → 8 sono il caso reale del video (cartella progetto-cliente-XYZ/); le percentuali per livello (~60% → ~90%) sono indicative, servono a capire fino a dove salire. Il test non ha un costo in euro: tutto gira in locale, l'unica spesa è il normale uso di Claude Code per il task-cavia.
