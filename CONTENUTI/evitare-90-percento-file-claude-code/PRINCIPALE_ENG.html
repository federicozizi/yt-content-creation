STEP 2 — TECHNIQUE 1

CLAUDE.md with "Output Discipline" section

What to show on screen

Open VS Code on your project. Show:

  • The CLAUDE.md file open (if it doesn't exist, create it)
  • Add at the end the "Output Discipline" section — paste from the materials example, scroll to show the list of banned patterns (TEST_*, NOTES_*, SCRATCH_*, etc.)
  • Save. Restart Claude Code.
  • Small test: "add a comment at the top of index.js". Verify Claude executes and does NOT create extra files.
What to say (verbatim)

"Technique number one, the simplest and most important: add an output-discipline section to your project's CLAUDE.md."

"CLAUDE.md, in case you're new, is a file Claude reads first in every session. It's the project's 'constitution'. Works VERY well if written well — Claude respects it by default."

"I add a section called 'Output Discipline' with three things. First: explicit list of file patterns it must NEVER create — TEST with underscore all caps, NOTES, SCRATCH, debug with underscore, summary with underscore. Second: rule on summaries — never create summaries as files, give them to me by voice in chat. Third: rule on reasoning — if you need to think about intermediate states, use internal thinking, not scratch files on disk."

"Save. Restart a new Claude Code session to make sure it reloads the file. Small test: 'add a comment at the top of index.js'. Boom, Claude executes, modifies one file, no extras. Technique one applied in ten minutes, blocks about sixty percent of useless files. Good start."

STEP 3 — TECHNIQUE 2

Deny patterns in settings.json

What to show on screen

Sequence:

  • Open .claude/settings.json of the project (or create it). Show the "permissions" section
  • Add "deny" section with patterns from esempio-settings.json in materials
  • Save
  • Test: explicitly ask Claude "create a file NOTES_test.md". Show the "Permission denied" error — the rule works.
What to say (verbatim)

"Technique number two: deny patterns in settings.json. This works at a completely different level from the first one — it's not in the prompt, it's in the system. Claude CAN try to write a banned file, but the Write tool fails with 'Permission denied' and he notices."

"I add to the project's settings.json a 'permissions' section with 'deny' and inside the list of patterns, written in glob format — so with asterisks. Something like Write parenthesis two asterisks slash TEST underscore asterisk. Translated: 'in any subfolder, no file whose name starts with TEST underscore'."

"The powerful thing about this technique: it bypasses the 'forgetfulness' problem of technique one. Even if Claude, in a long session, momentarily forgets the CLAUDE.md rules and tries to write a TEST underscore file, the system blocks it first."

"I verify: I explicitly ask Claude 'create a file NOTES underscore test dot md'. He tries. Write tool returns 'Permission denied'. Claude notices, tells me 'I can't create that file because it's blocked by your permissions'. Works. Technique two applied in five minutes."

STEP 4 — TECHNIQUE 3

PreToolUse Write hook — the active guard

What to show on screen

Same settings.json screen. Show adding the "hooks" section:

  • hooks.PreToolUse.matcher = "Write"
  • Hook calling an external Node script (e.g. ~/.claude/check-write-discipline.js)
  • Open the script in VS Code, show the logic: reads filename, blocks if banned pattern
  • Test: ask Claude "create a reasoning file on the next steps". Show Claude trying, hook blocking, Claude giving up without creating anything.

NB: the check-write-discipline.js script isn't in the materials (it's in the video, linked GitHub gist). For the director: have the gist ready during recording.

What to say (verbatim)

"Technique number three — this is the most technical of the five, but also the most powerful for those wanting maximum control. It's called PreToolUse Write hook."

"In short: a hook is a small script that Claude Code calls BEFORE executing a certain tool. In our case, before every Write. The script can look at what Claude is about to write — filename, content — and decide whether to let it pass or block it."

"I open the file ~/.claude/check-write-discipline.js. It's a small Node script, about thirty lines. Logic: takes the filename from the Write request, checks if it matches the banned patterns I listed, and if it matches prints 'BLOCKED' and returns an error exit code. Claude sees the error and gives up."

"Test: I ask Claude 'write a reasoning file on the next three project steps'. Claude tries to create 'reasoning underscore next steps dot md'. The hook intercepts, checks, BLOCK. Claude returns to his thinking and explains what he thinks directly in chat. Exactly what I wanted."

"The full script is in a GitHub gist linked in the materials — fifteen minutes of setup, max control forever."

STEP 5 — TECHNIQUE 4

Custom "Output minimalist" skill — the portable version

What to show on screen

Show:

  • Open terminal: mkdir -p ~/.claude/skills/output-minimalist
  • code ~/.claude/skills/output-minimalist/SKILL.md
  • Show the file content with frontmatter (name, description) and rules
  • Save. The skill is now at user level — applies to ALL your projects
  • Quick test on a second different project: verify the skill activates automatically when Claude detects opportunity
What to say (verbatim)

"Technique number four — the portable version of the first three. If techniques one, two, three are good for ONE specific project, the custom skill is the same idea but at your USER profile level, so it applies to all projects."

"What's a skill, quick recap. Claude Skills are expertise packages that Claude loads automatically when it recognizes they're needed. They were born for big things — like 'PDF management' or 'business workflow bundle'. But you can create your own, simple ones, for your purposes."

"I create the folder tilde slash dot claude slash skills slash output dash minimalist. Inside I create a SKILL.md file with a frontmatter — skill name, description — and then the rules, the same you already know but in skill form."

"Advantage over CLAUDE.md: I carry this to all my projects without repeating the output discipline section everywhere. Advantage over settings.json: more expressive, I can write more nuanced logic in natural language."

"Drawback: less deterministic. Skills 'activate when Claude thinks they're needed'. They work well ninety percent of the time, but if you want one hundred percent lockdown, pair with techniques one and two. Synergy, not replacement."

STEP 6 — TECHNIQUE 5

Reinforced initial prompt — the reminder that always works

What to show on screen

Show:

  • Open Claude Code, start a new session
  • As first message paste the "Output Discipline session rules" block from prompt-tipo.md in materials
  • Below the block, write your actual request
  • Show Claude confirming the rules and then executing the task cleanly
  • At the bottom, an overlay: "DISCIPLINE keyword for quick recall in long sessions"
What to say (verbatim)

"Technique number five, the last one — the reinforced initial prompt. It's the top of the stack. You put it ABOVE everything else."

"Simple idea: every time you start an important session, the FIRST message you send isn't your request — it's a reminder block of output discipline rules. Three paragraphs, copy-paste, ten seconds."

"What the block contains. Summary of rules — no scratch files, no notes, no debug. Explicit exceptions — 'if I ask create file X, do it'. And a recall keyword I use, called 'DISCIPLINE'. If during the session I see Claude reverting to old habits, I send him in chat just the word 'DISCIPLINE' and he reloads the rules."

"Works very well on LONG sessions. When Claude works for an hour straight on a complex task, sometimes task pressure makes him 'forget' the CLAUDE.md rules. The recall word brings him back in two seconds."

"The full block, including the prompt template, is in the materials in description. I save it as a snippet in my VS Code — launch in two keystrokes."
