How to avoid 90% of the useless files Claude Code generates

Method explainer: the 5 levers that discipline the output
What this document is. Supporting material to understand and explain the method while I record: how it's built, where each of the 5 techniques acts, and — above all — how far it drives down the number of files, which is the point of the video. It is not a script to read out: it's the mental model + the charts to keep in front of me (and to show on screen). I say the lines off the cuff.
The problem

Why Claude Code clutters the folder

It's not a bug: it's a training choice. The model is encouraged to "show its work" — it writes test plans, leaves notes, summaries of changes, scratch files of its reasoning. For an experienced developer that's sometimes useful; for a non-developer it's noise.

The result: you ask for something simple ("add a field to the form") and you end up with 5 files you never asked for (TEST_*.md, NOTES_*.md, scratch_*.py, debug_*.md, summary_*.md). After two weeks the folder is unreadable: hard to tell the real files apart, hard to make clean commits, and sometimes you delete the right one by mistake. The good news: this behavior can be disciplined. Claude is instructable — you just need the right levers, in the right spots.

Where you act

The method's architecture

Between your request and the file written to disk there are three spots where a useless file can be stopped. The 5 techniques aren't in a row: they're 5 nets with different mesh sizes placed on those three spots. The more nets you set, the less gets through.

Spot A — instructions (Techniques 1, 4, 5) Spot B — permission denied (Technique 2) Spot C — hook that blocks (Technique 3) Useless file stopped Clean folder

The three techniques at Spot A convince Claude not to want the file. If for some reason it tries anyway (long sessions, "forgetting"), Spot B refuses it at the system level and Spot C catches it with a script. It's defense in layers: redundant on purpose.

Piece by piece

The 5 techniques, one by one

1

Output Discipline in the CLAUDE.md Spot A · 10 min

What it is: an ## Output Discipline section in the project's CLAUDE.md — the file Claude reads first every session, the project's "constitution." Why it works: Claude respects the CLAUDE.md by default, so this is the lever with the best effort-to-effect ratio. How it's built: three rules — (a) an explicit list of banned names (TEST_*.md, NOTES_*.md, SCRATCH_*, debug_*, summary_*, duplicates like README_NEW.md); (b) no summary as a file, it gives it in chat; (c) no "reasoning" files — for intermediate state use TodoWrite, not files on disk. Ready-made block in esempio-claude-md.md. Limit: on long tasks it sometimes "forgets" it — which is why you need #2.

2

Deny patterns in the settings.json Spot B · 5 min

What it is: a permissions.deny section in .claude/settings.json that refuses writes to certain file names. Why it works: it acts at the system level, not the prompt level — even if Claude tries to write the file, the Write tool fails with "Permission denied" and it notices. It bypasses the "forgetting" of Technique 1. How it's built: the names are written in glob format (with asterisks): Write(**/TEST_*), Write(**/NOTES_*), Write(**/scratch*.*), and so on. A twin allow section protects your real tests (**/*.test.js, **/tests/**) so you don't block them by mistake. Ready-made file: esempio-settings.json. Active as soon as you save, no restart needed.

3

PreToolUse Write hook — the active guard Spot C · 15 min

What it is: a small script that Claude Code runs before every write. The most technical of the five, but also the most powerful. Why it works: Technique 2's deny only looks at the name; the hook also looks at the context — how many .md files are already in the folder, whether it's a duplicate (_v2, _copy), the content. How it's built: in settings.json, hooks.PreToolUse with matcher: "Write" calls node ~/.claude/check-write-discipline.js. The script reads the request, and if it violates the rules it prints "BLOCKED" and returns an error: Claude backs off and explains everything in chat. Director's note: the full script isn't in the materials — it's in the video with a linked GitHub gist. Keep it ready while recording.

4

"Output minimalista" Skill — the portable version Spot A · 15 min

What it is: the same rules packaged into a user-level skill (~/.claude/skills/output-minimalista/SKILL.md) that applies to all your projects. Why it works: skills activate on their own when Claude recognizes they're needed, without repeating the output-discipline section in every CLAUDE.md. You set it up once. How it's built: a SKILL.md file with frontmatter (name + description stating when to activate it) and the list of rules + the exception "if the user explicitly asks for a file, create it." Limit: less deterministic than the deny — it works most of the time, but to lock things down 100% pair it with Techniques 1 and 2. Synergy, not replacement.

5

Reinforced initial prompt — the recall that always works Spot A · 10 sec

What it is: the top of the stack. The first message of an important session isn't the request, it's a block reminding Claude of the output-discipline rules. Why it works: on long sessions the pressure of the task makes the CLAUDE.md rules "slip"; the reminder puts them back front of mind. How it's built: three things — a rules recap, explicit exceptions ("if I ask you to create file X, do it"), and a recall word: DISCIPLINE. If during the session Claude drifts back to old habits, I send just that word and it re-reads the rules. Ready-made block in prompt-tipo.md (with the "brutal task" variant for long sessions).

Honesty

When NOT to apply the method

Sometimes those files really are useful. If you're a developer and you use the test plans or debug logs to work, tailor the banned-name list — don't ban what you need.

The explicit exception is sacred. Every technique lets the file through if you ask for it ("create file X"): that's intentional. The method disciplines unrequested files, it doesn't tie your hands.

Deny patterns are touchy. A badly written glob blocks nothing (or blocks too much): test with a single pattern first and verify it actually works. And protect your real tests with the allow section.

The skill isn't 100% deterministic. It activates "when Claude thinks it's needed": great as a portable net, but to lock down a single project keep Techniques 1 and 2 anyway.

The folder you hand over

What's in the materials

It's the materiali/ folder the viewer downloads and that you zip up at the end of the video. It's not a program to run: it's ready-made examples and rules, to copy into the right places in your project. Here's how it's laid out and where each piece goes.

FileWhat it is / what it's for

esempio-claude-md.mdA ready-made example CLAUDE.md (Technique 1). It contains the ## Output Discipline block with the banned names and the rules. You copy it as CLAUDE.md into the root of your project: it's the "constitution" Claude reads first.

In one line: the pieces don't form an "input → program → output" flow, but a layered defense you assemble in your own project. The block of rules in esempio-claude-md.md goes into your project's CLAUDE.md (Point A); the deny patterns and the hook in esempio-settings.json go into .claude/settings.json (Points B and C); prompt-tipo.md you paste at the start of long sessions (Point A). The README.md is the map that explains which piece goes where. Technique 4 (the portable skill) is described in the README but has no dedicated file: you create it yourself in ~/.claude/skills/ following the instructions.

Try it — operational part

How to test the method (with the course materials)

There's no program to run here: there's a method. The test is meant to show, with your own eyes, that the techniques really do bring the file count down. Everything you need is in the materiali/ folder (esempio-claude-md.md, esempio-settings.json, prompt-tipo.md). You run it on a throwaway test project, so you risk nothing of your own.

  1. Create an empty test folder (e.g. progetto-cavia/) and open it in VS Code. It's the testing ground: whatever you generate here you can throw away.
  2. Apply the materials. Copy the ## Output Discipline block from esempio-claude-md.md into a CLAUDE.md in the folder; copy esempio-settings.json to .claude/settings.json (these are the deny patterns from Technique 2, plus the PreToolUse hook from Technique 3). Save: they take effect right away, no restart.
  3. Give Claude Code a task that usually messes up the folder — something like: “add an email field to the form and give me a summary”. It's the kind of request that, without discipline, would leave behind summary_*.md, NOTES_*.md, scratch files.
  4. Watch and count. Check that the usual useless files do NOT show up; also try explicitly asking for a junk file (e.g. “write a file summary_modifiche.md”) and watch the deny/hook refuse the write. Count the files before and after.

What you should see — when Claude tries to write a banned file, the Write tool is refused at the system level (real example from the patterns in esempio-settings.json):

> add an email field to the form, then write a file summary_modifiche.md

  Editing the form...  OK  (registrazione.js updated)

  Write(progetto-cavia/summary_modifiche.md)
  -- Permission denied: "Write(**/summary_*)" is in the deny list (settings.json)

  I've updated the form with the email field.
  I'll give you the summary of changes here in chat, not as a file:
   - added "email" (required) field to the registration form
   - added client-side and server-side validation

No extra files created.  summary_modifiche.md  ->  BLOCKED
Proof that the method works:
  • The folder stays clean: after the task there are only the real files (the edited form, the CLAUDE.md), no summary_* / NOTES_* / scratch → the Point A techniques convinced Claude not to want them.
  • Junk Writes get blocked: even when you force a banned name, the Write returns “Permission denied” and Claude backs off → the Technique 2 deny holds up against “forgetfulness”.
  • The file count stays low: on the same project from the video it goes from ~32 to ~8 files (of which the useless ones: from ~25 to ~0) → that's the ~90% of noise removed, the title's promise.

Two extra checks (optional):

• Turn one net off and on. Temporarily remove esempio-settings.json (rename it) and re-run the same task: the junk files start getting through again. Put it back: they vanish. You've seen Technique 2 switch on and off.

• The exception is sacred. Explicitly ask for a file you actually need (e.g. “create guida-utente.md”): it gets created with no trouble. The method disciplines the unrequested files, it doesn't tie your hands.

Note: the numbers 32 → 8 are the real case from the video (the progetto-cliente-XYZ/ folder); the per-level percentages (~60% → ~90%) are indicative, meant to show how far up to go. The test has no cost in euros: everything runs locally, the only spend is the normal use of Claude Code for the test task.
