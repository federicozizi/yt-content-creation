Hai mai messo Claude Code in un vero server di produzione?

Spiegazione del sistema: lo scraper notturno che gira da solo su un VPS
Cos'è questo documento. Materiale di supporto per capire e spiegare il sistema mentre registro: com'è fatto lo scraper che gira da solo su un server sempre acceso e — soprattutto — perché è accettabile lasciarlo girare senza nessuno davanti, che è il cuore del video. Non è un copione da leggere: è lo schema mentale + i diagrammi da tenere davanti (e da mostrare a schermo). Le frasi le dico a braccio.
In una frase

Di cosa parliamo

Ho messo Claude Code su un server vero, sempre acceso (un piccolo VPS da pochi euro al mese) e l'ho lasciato lavorare da solo, ogni notte, per 30 giorni. Il compito: visitare tre siti dei competitor di un cliente, leggere i prezzi, e mandare una mail solo quando qualcosa cambia davvero.

La differenza con l'uso "normale" di Claude Code sul tuo PC è enorme: qui non c'è nessuno a sorvegliare. Gira alle quattro del mattino mentre dormo. Quindi la domanda vera del video non è "come si installa", è: perché mi fido di lasciarlo girare da solo? La risposta non è "perché mi fido di Claude" — è perché ho costruito più reti di sicurezza una sotto l'altra.

Com'è fatto

Architettura del sistema

A sinistra il pezzo che fa partire tutto da solo. Al centro il server sempre acceso, dove Claude Code lavora ma dentro una gabbia (le barriere in rosso). A destra cosa produce. La parte importante non è il flusso: sono le barriere che circondano Claude.

Si avvia da solo (scheduling) Claude Code (il lavoratore) Le barriere (la gabbia) Quello che consegna

Fuori dal disegno, sopra a tutto, c'è una sesta barriera che non vive sul server: il tetto di spesa impostato nella console Anthropic. Anche se tutto il resto saltasse, oltre quella cifra la chiave smette di funzionare.

Pezzo per pezzo

Come funziona, pezzo per pezzo

1

Il server sempre acceso — il "negozio che non chiude mai"

Un piccolo computer in affitto in un data center (un VPS): Ubuntu, circa sei dollari al mese. Il motivo per non usare il PC di casa è banale: se stacchi la presa o va via la luce, di notte non parte niente. Il server invece è sempre acceso. Ci si entra da remoto solo con una chiave (in gergo SSH), mai con una password.

2

Claude Code "a mani libere" — il lavoratore senza schermo

Sul server gira claude --headless: è Claude Code senza la chat davanti, che esegue un compito scritto in un file (scraper-prompt.md) e poi si spegne. Quel file gli dice cosa fare passo passo: leggi i tre siti, prendi i prezzi, confrontali con ieri, scrivi il report. Il come di ogni passo lo decide lui — è qui che diventa "agente" e non semplice script.

3

La sveglia automatica — cron, lo "svuotabuste" che parte da solo

Una riga di pianificazione del sistema: 0 4 * * * vuol dire "ogni notte alle quattro". È il timer del server: a quell'ora lancia il comando, senza che io tocchi niente. Lo stesso meccanismo che farebbe partire un backup mentre dormi.

4

Cosa tocca e cosa produce — letture pubbliche, output verificabile

Claude legge le pagine dei competitor (WebFetch, dati pubblici), salva i prezzi in un piccolo archivio sul server (prezzi.db, un database SQLite), e scrive un report giornaliero. Manda la mail al cliente solo se trova variazioni sopra il 5%. Tutto il resto delle notti: silenzio, perché non è cambiato niente.

5

Il diario di bordo — il log, la scatola nera

A ogni esecuzione Claude scrive un diario su /var/log/claude-scraper.log: quando è partito, cosa ha deciso, cosa ha eseguito, quando ha finito. La mattina, se qualcosa è andato storto, ho la cronaca esatta. Se è andato tutto bene, ho i numeri per migliorare. Senza diario, sei cieco.

Il cuore del video

Perché è accettabile lasciarlo girare da solo

Questa è la tesi, ed è controintuitiva: non lo lascio girare perché mi fido di Claude. Lo lascio girare perché tra Claude e un disastro ho messo cinque barriere indipendenti, una sotto l'altra. Se Claude sbaglia — e in trenta giorni è successo — deve bucarle tutte nello stesso momento per fare danni. È lo stesso principio del formaggio svizzero: una fetta ha i buchi, ma cinque fette sovrapposte non lasciano passare niente.

Le cinque reti, dalla più esterna alla più vicina a Claude (la barra lunga = barriera più larga, che ferma più cose):

1 · Tetto di spesa
Limite € nella console Anthropic — oltre, la chiave si spegne
2 · Utente non-root
Utente claude con permessi minimi — il sistema rifiuta i comandi grossi
3 · Permessi allow/deny
Lista bianca/nera in settings.json: rm, sudo, Edit vietati
4 · Hook bloccante
Un controllo che, prima di ogni comando, blocca i pattern catastrofici
5 · Regole nel CLAUDE.md
La "costituzione" che Claude legge per primo: cosa non fare mai

Le barriere non si sostituiscono: si sommano. La regola scritta nel CLAUDE.md è la più gentile (Claude la legge e la rispetta); il tetto di spesa è la più brutale (non chiede permesso a nessuno). In mezzo, due livelli di permessi e un controllo automatico. Più una sesta rete invisibile qui: il dry-run, che provo prima di ogni messa in produzione per vedere cosa farebbe senza che faccia davvero niente.

Le barriere alla prova dei fatti — i tre incidenti dei 30 giorni e quale rete li ha fermati:

Cosa è andato stortoQuale barriera ha retto
Claude ha provato un comando di cancellazione fuori postoUtente non-root + hook → il comando non è mai partito
Una notte è entrato in loop su un sito lentoTetto di spesa → il danno si è fermato a una cifra nota
Un sito ha cambiato struttura, prezzi non estrattiLog + report → la mattina sapevo esattamente cosa correggere

Nessun incidente ha richiesto un intervento d'emergenza notturno. Ogni volta, una rete sotto ha contenuto il problema fino al mattino. Questo è ciò che rende sostenibile lasciarlo girare.

Onestà

Cosa il sistema NON è (e dove serve ancora un umano)

Sicuro non vuol dire infallibile. Le barriere riducono il danno, non azzerano gli errori. Claude può ancora sbagliare un prezzo o saltare un sito: per questo c'è il log e per questo la mattina do un'occhiata. Le reti servono a contenere il disastro, non a evitare ogni piccolo errore.

Non è "installa e dimentica". I siti cambiano struttura, qualcuno ti blocca l'accesso, una notte un server risponde lento. Il sistema regge da solo l'imprevisto fino al mattino, ma il manutentore — sui casi grossi etichettati BLOCKING ISSUE — resti tu.

Lo scraping è una zona grigia. Prima di puntarlo su un sito vero: leggi i termini di servizio, rispetta una frequenza moderata, scarica solo dati pubblici. Sul legale, in caso di dubbio, serve un avvocato — non Claude.

Sulle credenziali si gioca tutto. La ANTHROPIC_API_KEY sul server vale soldi veri: chiave dedicata, mai dentro Git, e se per sbaglio finisce online si revoca e si rigenera subito (cancellarla dalla storia non basta — i bot la trovano). Tutti i dettagli nel DISCLAIMER.md dei materiali.

La cartella che consegni

Cosa c'è nei materiali

È la cartella materiali/ che lo spettatore scarica e che tu zippi a fine video. Non c'è codice da far girare: sono i file di configurazione da copiare sul server, più le istruzioni. Ognuno con un ruolo preciso. Ecco com'è fatta e come i pezzi si parlano.

FileCos'è / a cosa serve
scraper-prompt.mdIl compito dell'agente: il prompt che il cron lancia ogni notte. Dice a Claude Code cosa fare passo-passo (apri il log, leggi la lista competitor, scarica le pagine, confronta i prezzi, scrivi il report, manda la mail). Contiene 3 placeholder da sostituire (gli URL dei competitor, l'email del cliente) e un esempio del file competitors.json.
claude-settings-produzione.jsonLe barriere di sicurezza: si copia in ~/.claude/settings.json sul server. Qui dentro c'è la lista di ciò che Claude può fare (allow) e ciò che gli è vietato (deny: niente rm, sudo, curl…), più gli hook: uno blocca i comandi distruttivi prima che partano, gli altri scrivono una riga di log a ogni mossa.
claude-md-produzione.mdLa costituzione del progetto: si copia come CLAUDE.md nella cartella sul server. Claude lo legge per primo a ogni avvio. Mette nero su bianco le 5 regole (no azioni distruttive, sempre log, niente dati personali, dry-run, tetto al consumo) e quando deve fermarsi e chiamare un umano.
README.mdLa guida passo-passo per il pubblico: dal VPS vuoto al sistema schedulato. Comandi di installazione, dove incollare ogni file qui sopra, e le 5 regole spiegate.
DISCLAIMER.mdL'avviso sulla sicurezza: come proteggere la ANTHROPIC_API_KEY e il server, cosa NON tenere sulla macchina, il lato legale dello scraping, e cosa fare in caso di emergenza.

In una riga: scraper-prompt.md definisce il compito, claude-settings-produzione.json e claude-md-produzione.md impongono le barriere di sicurezza (cosa può e cosa non può fare), il cron sul server lo schedula ogni notte e il file di log registra ogni esecuzione. README e DISCLAIMER sono le istruzioni e le precauzioni.

Quello che non trovi nei materiali perché nasce sul server quando il sistema gira: il file di log /var/log/claude-scraper.log, il database dei prezzi prezzi.db, la cartella reports/ coi report giornalieri, lo stato last_run_state.json e la lista competitors.json (la prepari tu al primo setup partendo dall'esempio nel prompt). Non ci sono all'inizio: sono il frutto del lavoro notturno.

Provalo — parte operativa

Come testare il sistema (coi materiali del corso)

Tutto il necessario è nella cartella materiali/ (il CLAUDE.md, il settings.json, il prompt del task). La regola d'oro è una: prima di lasciarlo girare da solo, verifichi a mano che le reti di sicurezza tengano. Non si schedula niente finché non hai visto, con i tuoi occhi, che un comando distruttivo viene bloccato. Questa è la sequenza esatta.

  1. Prova a mano, sul server, lo stesso comando che girerà di notte — ma in sicurezza. Da dentro ~/scraper lancia il dry-run: claude --dry-run -f scraper-prompt.md. Claude esegue tutta la logica (legge i siti, calcola le variazioni) ma non scrive nel database, non manda mail, non tocca lo stato: ti mostra solo cosa farebbe. È il collaudo a vuoto prima della messa in produzione.
  2. Controlla che acceda solo in lettura alle fonti e scriva solo dove deve. Nel log (/var/log/claude-scraper.log) e nell'output del dry-run le pagine dei competitor risultano solo lette (WebFetch), e le uniche scritture sono dentro /home/claude/scraper/ — il database prezzi.db, i reports/, il log. Niente scritture fuori da lì: lo impone la lista allow in ~/.claude/settings.json.
  3. Prova una barriera: lancia di proposito un'azione distruttiva e guardala fallire. Sempre da ~/scraper, chiedi a Claude in modalità interattiva un comando vietato — ad esempio cancellare il log con rm -rf /var/log/claude-scraper.log. Due reti indipendenti lo fermano: la regola deny Bash(rm:*) in settings.json e l'hook PreToolUse, che prima di ogni comando Bash intercetta i pattern catastrofici (rm -rf, sudo, mkfs…) e risponde BLOCKED: comando distruttivo. Il comando non parte.
  4. Controlla che il tetto di spesa sia impostato. Apri la console Anthropic (Settings → Billing → Usage Limits) e verifica che ci sia un soft limit (ti manda una mail, esempio 50 USD) e soprattutto un hard limit: oltre quella cifra la chiave smette di funzionare. È la rete che non vive sul server — regge anche se tutto il resto saltasse, ad esempio se Claude entrasse in loop su un sito lento.
  5. Solo adesso schedula, e controlla il log dopo la prima notte. Metti in crontab -e la riga 0 4 * * * cd /home/claude/scraper && claude --headless -f scraper-prompt.md >> /var/log/claude-scraper.log 2>&1. La mattina dopo apri /var/log/claude-scraper.log e l'ultimo reports/<data>.md: devi trovare un RUN START / RUN END puliti. Se il cron non è partito, controlla con grep CRON /var/log/syslog (spesso è un problema di PATH dentro il cron).

Cosa devi vedere quando provi la barriera del passo 3 (esempio di output nel terminale):

> rm -rf /var/log/claude-scraper.log

[PreToolUse:Bash] controllo pattern distruttivi...
BLOCKED: comando distruttivo
Permission denied by deny rule: Bash(rm:*)

Il comando NON e' stato eseguito.
[OK] La barriera ha retto: il file e' ancora li'.

E così appare invece un giro regolare nel log, dopo una notte andata bene:

=== RUN START 2026-06-15T04:00:03Z ===
Trigger: cron
Goal: scraping prezzi 3 competitor, alert variazioni > 5%
[WebFetch] competitor A ... ok
[WebFetch] competitor B ... ok
[WebFetch] competitor C ... ok
Variazione > 5% trovata: [Competitor A] Prodotto X: 49.90 -> 39.90 (-20%)
Report scritto in reports/2026-06-15.md
Mail inviata al cliente.
=== RUN END 2026-06-15T04:03:41Z | status: success | comandi eseguiti: 14 ===
La prova che le reti tengono:
  • Ha solo letto le fonti: nel log i competitor compaiono come WebFetch, mai come login o scrittura sui loro siti → accesso in sola lettura.
  • Ha prodotto report e log verificabili: reports/<data>.md aggiornato e RUN START/RUN END nel log → sai sempre cosa ha fatto.
  • Il comando distruttivo è stato bloccato da hook + regola deny, e oltre il tetto di spesa la chiave si spegne da sola → il disastro è contenuto prima che accada.

Le credenziali: la ANTHROPIC_API_KEY vive in ~/.claude/env sul server e non va mai committata su Git — se per sbaglio finisce online, si revoca e si rigenera subito (tutti i dettagli nel DISCLAIMER.md dei materiali).
