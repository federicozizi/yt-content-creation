In one sentence

What this is about

I put Claude Code on a real, always-on server (a small VPS costing a few euros a month) and let it work on its own, every night, for 30 days. The job: visit three of a client's competitor websites, read the prices, and send an email only when something actually changes.

The difference from the "normal" use of Claude Code on your PC is huge: here nobody is watching. It runs at four in the morning while I sleep. So the real question of the video isn't "how do you install it", it's: why do I trust letting it run on its own? The answer isn't "because I trust Claude" — it's because I built several safety nets stacked one under the other.

Piece by piece

How it works, piece by piece

1

The always-on server — the "shop that never closes"

A small rented computer in a data center (a VPS): Ubuntu, about six dollars a month. The reason for not using your home PC is trivial: if you unplug it or the power goes out, nothing fires at night. The server, instead, is always on. You log in remotely only with a key (SSH), never with a password.

2

Claude Code "hands-free" — the worker with no screen

On the server runs claude --headless: it's Claude Code with no chat in front of it, executing a task written in a file (scraper-prompt.md) and then shutting down. That file tells it what to do step by step: read the three sites, grab the prices, compare with yesterday, write the report. The how of each step it decides on its own — this is where it becomes an "agent" and not a plain script.

3

The automatic alarm — cron, the "self-starting cleaner"

One line of system scheduling: 0 4 * * * means "every night at four". It's the server's timer: at that hour it launches the command, without me touching anything. The same mechanism that would fire off a backup while you sleep.

4

What it touches and what it produces — public reads, verifiable output

Claude reads the competitors' pages (WebFetch, public data), saves the prices in a small store on the server (prezzi.db, a SQLite database), and writes a daily report. It emails the client only if it finds changes above 5%. All the other nights: silence, because nothing changed.

5

The flight log — the log, the black box

On every run Claude writes a journal to /var/log/claude-scraper.log: when it started, what it decided, what it executed, when it finished. In the morning, if something went wrong, I have the exact account. If everything went fine, I have the numbers to improve. Without a journal, you're blind.

The heart of the video

Why it's acceptable to let it run on its own

This is the thesis, and it's counterintuitive: I do not let it run because I trust Claude. I let it run because between Claude and a disaster I put five independent barriers, one under the other. If Claude makes a mistake — and in thirty days it did — it has to break through them all at the same time to do damage. It's the Swiss cheese principle: one slice has holes, but five stacked slices let nothing through.

The five nets, from the outermost to the one closest to Claude (the longer the bar = the wider the barrier, the more it stops):

1 · Spending cap
€ limit in the Anthropic Console — beyond it, the key shuts off
2 · Non-root user
A claude user with least privilege — the system refuses the big commands
3 · allow/deny permissions
Allow/deny list in settings.json: rm, sudo, Edit forbidden
4 · Blocking hook
A check that, before every command, blocks the catastrophic patterns
5 · Rules in the CLAUDE.md
The "constitution" Claude reads first: what never to do

The barriers don't replace each other: they add up. The rule written in the CLAUDE.md is the gentlest (Claude reads it and respects it); the spending cap is the most brutal (it asks nobody for permission). In between, two layers of permissions and an automatic check. Plus a sixth, invisible net here: the dry-run, which I try before every push to production to see what it would do without it actually doing anything.

The barriers put to the test — the three incidents of the 30 days and which net stopped them:

What went wrongWhich barrier held
Claude tried a misplaced deletion commandNon-root user + hook → the command never ran
One night it got into a loop on a slow siteSpending cap → the damage stopped at a known figure
A site changed its structure, prices not extractedLog + report → in the morning I knew exactly what to fix

No incident required a middle-of-the-night emergency. Each time, a net below contained the problem until morning. This is what makes it sustainable to let it run.

Honesty

What the system is NOT (and where a human is still needed)

Safe doesn't mean infallible. The barriers reduce the damage, they don't zero out the mistakes. Claude can still get a price wrong or skip a site: that's why there's the log and that's why in the morning I take a look. The nets are there to contain the disaster, not to avoid every small error.

It's not "install and forget". Sites change their structure, someone blocks your access, one night a server responds slowly. The system handles the unexpected on its own until morning, but the maintainer — on the big cases tagged BLOCKING ISSUE — stays you.

Scraping is a gray area. Before pointing it at a real site: read the terms of service, respect a moderate frequency, download only public data. On the legal side, when in doubt, you need a lawyer — not Claude.

Credentials are where everything is at stake. The ANTHROPIC_API_KEY on the server is worth real money: a dedicated key, never inside Git, and if it accidentally ends up online you revoke and regenerate it immediately (deleting it from history isn't enough — bots find it). All the details in the DISCLAIMER.md of the materials.

The folder you hand over

What's in the materials

It's the materiali/ folder the viewer downloads and that you zip up at the end of the video. There's no code to run: these are the configuration files to copy onto the server, plus the instructions. Each with a precise role. Here's how it's laid out and how the pieces talk to each other.

FileWhat it is / what it's for
scraper-prompt.mdThe agent's task: the prompt that cron launches every night. It tells Claude Code what to do step by step (open the log, read the competitor list, download the pages, compare prices, write the report, send the email). It contains 3 placeholders to replace (the competitor URLs, the client's email) and an example of the competitors.json file.
claude-settings-produzione.jsonThe safety barriers: you copy it to ~/.claude/settings.json on the server. Inside is the list of what Claude can do (allow) and what is forbidden (deny: no rm, sudo, curl…), plus the hooks: one blocks destructive commands before they run, the others write a log line on every move.
claude-md-produzione.mdThe project's constitution: you copy it as CLAUDE.md into the folder on the server. Claude reads it first on every start. It spells out the 5 rules (no destructive actions, always log, no personal data, dry-run, a cap on spending) and when it must stop and call a human.
README.mdThe step-by-step guide for the public: from an empty VPS to the scheduled system. Installation commands, where to paste each file above, and the 5 rules explained.
DISCLAIMER.mdThe safety note: how to protect the ANTHROPIC_API_KEY and the server, what NOT to keep on the machine, the legal side of scraping, and what to do in an emergency.

In one line: scraper-prompt.md defines the task, claude-settings-produzione.json and claude-md-produzione.md impose the safety barriers (what it can and can't do), the cron on the server schedules it every night, and the log file records every run. README and DISCLAIMER are the instructions and the precautions.

What you won't find in the materials because it's born on the server when the system runs: the log file /var/log/claude-scraper.log, the price database prezzi.db, the reports/ folder with the daily reports, the last_run_state.json state and the competitors.json list (you prepare it yourself at the first setup, starting from the example in the prompt). They're not there at the start: they're the fruit of the nightly work.

Try it — operational part

How to test the system (with the course materials)

Everything you need is in the materiali/ folder (the CLAUDE.md, the settings.json, the task prompt). The golden rule is one: before letting it run on its own, verify by hand that the safety nets hold. You don't schedule anything until you've seen, with your own eyes, a destructive command get blocked. This is the exact sequence.

  1. Run by hand, on the server, the same command that will run at night — but safely. From inside ~/scraper launch the dry-run: claude --dry-run -f scraper-prompt.md. Claude runs the whole logic (reads the sites, computes the changes) but does not write to the database, does not send mail, does not touch the state: it only shows you what it would do. It's the dry test before going to production.
  2. Check that it only reads the sources and only writes where it should. In the log (/var/log/claude-scraper.log) and in the dry-run output the competitor pages appear only as read (WebFetch), and the only writes are inside /home/claude/scraper/ — the prezzi.db database, the reports/, the log. No writes outside of there: that's enforced by the allow list in ~/.claude/settings.json.
  3. Test a barrier: deliberately launch a destructive action and watch it fail. Still from ~/scraper, ask Claude in interactive mode for a forbidden command — for example deleting the log with rm -rf /var/log/claude-scraper.log. Two independent nets stop it: the deny rule Bash(rm:*) in settings.json and the PreToolUse hook, which before every Bash command intercepts the catastrophic patterns (rm -rf, sudo, mkfs…) and replies BLOCKED: comando distruttivo. The command does not run.
  4. Check that the spending cap is set. Open the Anthropic console (Settings → Billing → Usage Limits) and verify there is a soft limit (it emails you, example 50 USD) and above all a hard limit: beyond that figure the key stops working. It's the net that doesn't live on the server — it holds even if everything else failed, for instance if Claude got stuck in a loop on a slow site.
  5. Only now schedule, and check the log after the first night. Put in crontab -e the line 0 4 * * * cd /home/claude/scraper && claude --headless -f scraper-prompt.md >> /var/log/claude-scraper.log 2>&1. The next morning open /var/log/claude-scraper.log and the latest reports/<date>.md: you should find a clean RUN START / RUN END. If cron didn't fire, check with grep CRON /var/log/syslog (often it's a PATH problem inside cron).

What you should see when you test the barrier in step 3 (sample terminal output):

> rm -rf /var/log/claude-scraper.log

[PreToolUse:Bash] checking destructive patterns...
BLOCKED: comando distruttivo
Permission denied by deny rule: Bash(rm:*)

The command was NOT executed.
[OK] The barrier held: the file is still there.

Proof that the nets hold:
  • It only read the sources: in the log the competitors appear as WebFetch, never as a login or a write on their sites → read-only access.
  • It produced verifiable report and log: reports/<date>.md updated and RUN START/RUN END in the log → you always know what it did.
  • The destructive command was blocked by hook + deny rule, and beyond the spending cap the key shuts itself off → the disaster is contained before it happens.

Credentials: the ANTHROPIC_API_KEY lives in ~/.claude/env on the server and must never be committed to Git — if it accidentally ends up online, revoke and regenerate it immediately (all the details in the DISCLAIMER.md of the materials).
